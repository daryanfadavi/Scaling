Why this was dangerous. A failed call is treated as "do nothing", so the bug would not crash anything. The cluster would look calm while the model never made a single decision, which is easy to mistake for a controller that works but rarely needs to act.

In simple terms: temperature is a dial for how random a model's answers are. We set it to 0 so the same situation gets the same answer. This model now refuses the setting altogether.

The fix (commit b42ce90): stop sending it, log the setting in the first line of every run, add a unit test. The cost: answers are a little less repeatable, so repeating each experiment matters more.

What the results mean, in plain words

The pipeline works end to end. Load goes in, numbers come out, the model reads them, the guardrails check its answer, and real pods are added. In 17 decisions: no errors, no unreadable answers, no blocked actions. Out of 5,202 requests, none failed.

What went well

  • Quiet when nothing happens: it held 1 pod through the idle period and said why.
  • Reacted when load arrived: one pod hit 257% CPU; within a tick the model added 2 pods and CPU fell to 114%.
  • Fast: each model call took about 1 s, so the 15 s tick sets the delay, not the model.

What to watch

  • The second scale-up (3 → 4 at 164 s) looks like a mistake. The load was already back to its quiet level. The model saw 35 req/s after 49, 54 and 51, a falling number, and called it a "spike".
  • Latency was never in danger. Worst p95 was 25 ms against 300 ms.
  • It never scaled down. The 120 s cooldown outlasted the run.
  • One run is an anecdote.
Two smaller things we noticed
  • "Controller didn't exit in time; sending SIGKILL" appeared at the end, but the controller had logged stopped in the same second as the stop signal. The runner (experiments/run_experiment.py, not ours) probably mistook a finished-but-uncollected process for a live one. Not confirmed. Harmless apart from a 20 s delay and a misleading line. Worth telling Daryan.
  • Bytecode in the hash. Unit tests leave __pycache__ files in controllers/llm/, and the runner hashes that folder into metadata.json. It only affects the recorded hash, not the results. Delete them before a real experiment.

  • The model never saw the plan; it saw a one-minute average, and that lag is what fooled it.
Literature · Nov 2026

How could an LLM actually run autoscaling?

A scan of 15 papers (the three most relevant read in full), plus the project's core background reading.

How much to trust this tab. The paper summaries come from the team page docs/phase1_run.html. The detailed notes it cites (docs/research/llm_controller_architectures.md) are not in the repo, and we have not re-checked the papers. Numbers below are the authors' own claims.

First finding: almost nobody has done this

Most"LLM + autoscaling" papers are about scaling LLMs (GPU model serving), not using an LLM as the scaler.
1paper found that runs an LLM controller head-to-head against Kubernetes HPA (SAIR).
0papers that test an LLM using human operator context against HPA. That is our gap.

Five ways to put an LLM in the loop

Autoscaling is like driving a car. Click a card for more.

A · where we are🚗The Driver

Every 15 s the LLM reads the dashboard and says "add 2 pods" or "hold".

Simple and explainable, but one LLM call per decision. Note: our cluster controller also shows the model its last 5 decisions, so it is already part of the way to design B.
click for more
B📓Driver with a diary

Same, but the prompt includes past decisions and how they turned out, so it "learns" without retraining.

Example: SAIR. Its authors report that removing the diary made results about 17% worse.
click for more
C🧑‍✈️Manager of the autopilot

HPA keeps driving. Every few minutes the LLM adjusts HPA's settings (target %, min/max).

Safe by design, cheap (few calls), and untested for autoscaling in the papers we found. This is the project's stated fallback architecture.
click for more
D🌦️Weather forecaster

The LLM only predicts upcoming traffic; a normal controller scales ahead of it.

Examples: Time-LLM, Chronos. Uses the model for what it may be good at (forecasting), not for control.
click for more
E🩺Doctor

The LLM first diagnoses why things are slow, then picks a fix.

Example: ORACL. Turns metrics into words ("CPU: High"), finds the root cause, then chooses an action.

The three papers that matter most

SAIR

NeurIPS 2026 · design B
What: an off-the-shelf LLM decides scaling every 30 s; the prompt includes about 15 past decisions and their outcomes.
Result: beat HPA on tail latency by 6–50% on a real cluster; removing the diary made it about 17% worse.
For us: the closest setup to ours; its limits (max ±2 pods, cooldowns) resemble our guardrails.
Doesn't say which LLM it used. The "97% cheaper" headline is against its weakest baseline.

ORACL

Univ. of Melbourne, 2026 · design E
What: metrics become words, the LLM finds the root cause, then picks a fix.
Result: lower latency than simple threshold scalers on a microservice shop app.
For us: two ideas to borrow: Low/Med/High labels as input, and "diagnose before you act".
Uses a specially trained LLM, never tested against real HPA, and some abstract numbers aren't backed up in the paper.

Scaling under long startup delays

CloudCom 2026 · no LLM
What: new pods take time to start, so a reactive controller is always late. Predict traffic one startup-delay ahead and scale early.
Result: that one idea cut slow responses about 14×.
For us: our simulator has the same startup delay (2 ticks). It changes how we should test.
Simulation plus a small hardware test; scaling back down is left unsolved.

Why this matters for our experiment

If the LLM beats HPA on "campaign in 90 s"…

…was it because it understood the message?

or
…because it just scaled early?

A 20-line "look ahead" controller might do the same with no LLM at all.

So we need a simple non-LLM look-ahead baseline. If the LLM still wins against that, the language understanding helped, not just the timing.

Core background reading from the onboarding docs

DeepRM (Mao et al., 2016)

A reinforcement-learning agent learns a resource policy from experience. Our framing borrows its structure: system state → policy → decision. Honest answer to "why not RL?": RL can learn strong policies but needs environment interaction and reward engineering, and doesn't take qualitative context naturally.

Kubernetes HPA (docs)

Our primary baseline. We need to know its formula, tolerances, stabilization windows and scale-up/down policies well enough to explain why it does or doesn't handle a workload.

ReAct (Yao et al., 2022)

How to interleave reasoning with discrete actions. Useful for the controller's prompt and action loop.

LLM + RL for cyber operations (El Mezouar et al.)

One of few examples of LLM-augmented decisions in a changing, adversarial environment. Structurally similar to ours. DeathStarBench (a realistic microservice suite) is noted for later, not needed yet.

What format do we give the LLM?

No one agrees

JSON, table or plain sentences: the best choice depends on the model, and no study tested it for control.

Numbers in sentences hurt

Tables or JSON tend to beat numbers buried in prose, and format changes token count, so speed and cost too.

So we test it ourselves

Same controller, three formats (JSON / table / Low-Med-High words). A cheap experiment with a real answer.

Our take

Insights and what to do next

What our first results and the research suggest, what to investigate next, and how to handle the LLM controller from here.

These are recommendations from reading the code, our one test run, and the team's research summary. They are not findings. Agree them with the team (especially Daryan and Max) before acting.

A · What our first results suggest

Risk Failure looks like calm

A failed model call becomes "do nothing". The temperature bug would have hidden behind that. Do: have every run count failed calls and print a loud summary; treat a run with failed calls as invalid, not as "the LLM rarely acts".

Evidence Lagging averages fool the model

It saw a falling request rate and called it a spike, despite a warning in its prompt and 3 ticks of history. Now built: cluster-v2-trend computes an explicit trend from the controller's own history, so it stays fair. In the prompt lab it fixed this exact misread (tab 7), but it was designed on that one example, so it still needs held-out situations and cluster repeats.

Evidence The ramp was too gentle

Worst p95 was 25 ms against 300 ms, even at one pod and 257% CPU. A test that can't hurt can't show a benefit. Do: use the harsher shapes already on main: step_up, sudden_spike, daily_wave, random_bursts.

Question Is the startup delay really long here?

New pods were ready by the next 15 s reading after the first scale-up. The simulator assumes 30 s and the startup-delay paper assumes long delays. If real startup is short, look-ahead matters less on this cluster. Do: measure it properly (time from scale command to ready, several times). This is one observation, so treat it as a lead.

Evidence Cost is not the blocker

Each call took about 1 s and 17 calls cost very little. Do: log tokens and cost per run anyway, since the team asked whether to score API calls.

Evidence Output is no longer fully repeatable

Without temperature 0, the same situation can get different answers. Do: at least 3 repeats per condition, and report the spread, not just one run.

B · What to research next, in order

1

Test the core hypothesis: does context help?

The project's strongest claim is that an LLM can use qualitative context (a campaign is coming) that HPA can't. Our cluster controller cannot read any context yet; it is metrics plus a 5-decision history. Max's separate script has a context variant (llm_context). Run spike_with_warning on the real cluster, with a matching run that has no note and one with a misleading note (a campaign that never comes).

Why firstNeeds a design decision

Care needed: notes must reach the controller through a neutral channel (for example a notes file it polls), never through scenario names or configs, or the fairness rule breaks. Propose the design to Daryan before building.

2

Add the controls that separate "LLM" from "information"

(a) A non-LLM look-ahead baseline (from the startup-delay paper). (b) A scheduled baseline that pre-scales at a time the operator gives it; a version already exists in the simulator (controller/scheduled_baseline.py). If a 20-line controller matches the LLM, the model isn't what helped; the information is.

Why fairness of the final claim
3

Harsher scenarios, with repeats, on one machine

All five scenarios, at least 3 repeats each, run on the machine Daryan uses for final numbers so results are comparable. Compare HPA, KEDA and the LLM on the same shapes. Report cost (pod-minutes) as well as latency.

4

Prompt experiments, one change at a time

Candidates: explicit trend line (see A), history length (SAIR's diary result suggests it matters), input format (JSON / table / Low-Med-High words), "diagnose then act" wording (ORACL). Each change gets a new PROMPT_VERSION and its own repeats.

5

The fallback architecture: LLM as manager of HPA

If direct control proves too slow, jumpy or unreliable, let HPA do the second-to-second work while the LLM adjusts its settings every few minutes. Cheap, safe, and not published for autoscaling as far as our scan found.

6

Other models and settings

Haiku 4.5 is the default. Compare one or two other models (OpenRouter is wired in; pin the upstream provider so runs are reproducible). Note that this model no longer accepts a temperature setting, so decide the policy for all models and write it down.

C · How to handle the LLM controller

Do

  • Treat controllers/llm as the one cluster controller. It follows the shared plugin contract (runner, telemetry, bounds).
  • Freeze before collecting data: model, prompt version, cooldowns. They are logged in the first line of controller.log.
  • Change one thing at a time and bump PROMPT_VERSION each time.
  • Keep guardrails strict. Raw model output never reaches the Kubernetes API.
  • Report negative results. "HPA wins, except when X" is a valid, publishable outcome.
  • Flag fairness-affecting changes in the PR, as AGENTS.md asks.
  • Clean up before real runs: delete __pycache__ in controllers/llm/.

Don't

  • Don't let the controller learn the scenario: no reading of configs, results or run names.
  • Don't compare against HPA numbers from a different setup (the Phase 1 numbers are history).
  • Don't draw conclusions from one run or from a scenario that never stresses latency.
  • Don't change shared settings (cluster, app, scenarios, telemetry) to make the LLM look better.
  • Don't commit .env, experiments/results/ or setup.log.
  • Don't average away the failures: count and report failed or invalid calls.

Coordinate with Max. The branch feature_Max_llm_controller adds experiments/k8s_run.py, a separate way to run the simulator's LLM controller on the live cluster. Per its setup notes it scrapes CPU directly instead of using the shared runner and telemetry, and it uses a scale-down cooldown of 4 ticks (60 s) while ours is 120 s. Two LLM controllers with different timers and inputs will not give comparable results. Agree one set of settings, and decide whether k8s_run.py stays as a development tool or is retired once our plugin has the context feature.

6 · What this suggests about prompting

  

    
Finding The baseline misreads its own history table
At the live mistake it quoted old rows as current ("CPU spiking to 137%") and called a flat p95 "trending upward". A table of numbers does not say which way things are heading. In Test A, a trend line, a longer history or an outcomes column all fixed it; words next to the numbers did not.

    
Finding Fixes designed on one example do not transfer
The 15-decision history fixed Test A and was the most trigger-happy prompt in Test B. Winners on the dev set are not winners on held-out data. This is why keeping a held-out set matters, and why one example is never enough.

    
Lead The trend line generalised best
In Test B it matched the baseline's first scale-up, scaled up less than the long-history and outcomes prompts, and asked to remove pods once the load fell. It is the prompt to take into the cluster repeats, with the caution that it was also the one we designed after seeing the bug.

    
Lead History cuts both ways
No history made the model passive (it never scaled up in Test B). A long history made it jumpy. SAIR's "diary helps" is true only if the diary can be read; a short, explicit summary of direction seems to read better than rows of numbers.

    
Finding Format compliance is a prompting problem
Code fences, missing fields and out-of-range amounts caused 1 invalid answer in the cluster run and 3 in the lab, all from the idle one-pod situation. Candidate fix: say the bounds plainly ("at the minimum, answer NO_CHANGE") and show one example reply. This needs no parser change.

    
Method Answers vary, so repeat
The same prompt gave different answers to the same moment. The model no longer accepts a temperature setting, so one answer proves little. Use 5 or more answers per situation in the lab and 3 or more repeats on the cluster.

  


  
7 · How to run prompt work from here

  
No model weights are trained in this project. "Training" here means prompt engineering plus evaluation, so the discipline is the evaluation:

    
    
      
  1. Fix the score first: SLA-violation ticks, pod-minutes, flaps, and failed or invalid model calls (summarize_cluster.py).
    2. 
      
  2. Keep two sets of situations: a dev set to design prompts on, and a held-out set to judge them. We now have one of each (experiments/prompt_lab_cases/). Never design a prompt on the held-out set.
    3. 
      
  3. One change per variant, a new name, and a unit test that it differs only by that change.
    4. 
      
  4. Lab to shortlist, cluster to confirm: at least 5 answers per situation in the lab, at least 3 repeats per scenario on the cluster, on the machine Daryan uses for final numbers.
    5. 
      
  5. Never use a run with failed model calls, and report prompts that did not help.
    6. 
      
  6. Later, optionally: search prompts automatically against the lab once the held-out set is big enough to trust.
    7.

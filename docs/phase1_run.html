Part 2 · LLM controller research

How could an LLM actually run autoscaling?

What we found from a literature scan (Nov 2026): 15 papers screened, and the three most relevant read in full.

In Part 1, HPA followed one rule: "keep CPU near 60%". Our project asks whether an LLM can make better scaling decisions, especially when a human tells it something a CPU graph can't, like "a marketing campaign launches in 90 seconds."

Before building, we wanted to know: how have other people put an LLM in charge of a system like this?

First finding: almost nobody has done this yet

Most
"LLM + autoscaling" papers are about scaling LLMs (GPU model serving), not using an LLM as the scaler
1
paper we found that runs an LLM controller head-to-head against Kubernetes HPA (SAIR)
0
papers that test an LLM using human operator context against HPA: that's our gap

Five ways to put an LLM in the loop

Every design we found fits one of these. Think of autoscaling as driving a car.

A · ours today🚗The Driver

Every 15 s, the LLM looks at the dashboard and says "add 2 pods" or "hold".

Simple and explainable, but an LLM call on every decision.
B📓Driver with a diary

Same, but the prompt includes past decisions and how they turned out, so it learns without retraining.

e.g. SAIR
C🧑‍✈️Manager of the autopilot

HPA keeps driving. Every few minutes the LLM adjusts HPA's settings (target %, min/max).

Safe by design; untested for autoscaling
D🌦️Weather forecaster

The LLM only predicts upcoming traffic; a normal controller scales ahead of it.

e.g. Time-LLM, Chronos
E🩺Doctor

The LLM first diagnoses why things are slow, then picks a fix.

e.g. ORACL

The three papers that matter most

SAIR

NeurIPS 2026 · Driver with a diary (B)
What: an off-the-shelf LLM decides scaling every 30 s. Its prompt includes ~15 past decisions and their outcomes.
Result: beat HPA on tail latency by 6–50% on a real cluster. Removing the diary made it ~17% worse.
Why it matters to us: the closest setup to ours, and its safety limits (max ±2 pods, cooldowns) match our guardrails almost exactly.
⚠️ Doesn't say which LLM it used. The "97% cheaper" headline is against its weakest baseline.

ORACL

Univ. of Melbourne, 2026 · Doctor (E)
What: turns metrics into words ("CPU: High"), asks the LLM to find the root cause, then choose a fix.
Result: lower latency than simple threshold scalers on a microservice shop app.
Why it matters to us: two ideas to borrow: Low/Med/High labels as input, and "diagnose before you act".
⚠️ Uses a specially trained LLM (not like ours), never tested against real HPA, and some abstract numbers aren't backed up in the paper.

Scaling under long startup delays

CloudCom 2026 · no LLM in the controller
What: new pods take time to start, so a controller that only reacts is always late. Predict traffic one startup-delay ahead and scale early.
Result: that one idea cut slow responses about 14×.
Why it matters to us: our simulator has the same startup delay (2 ticks). See below. This changes how we should test.
⚠️ Simulation plus a small hardware test; "scaling back down" is left unsolved.

Why this matters for our experiment

If the LLM beats HPA on a "campaign in 90 s" spike…

…was it because it understood the message?

or
…was it just because it scaled early?

A 20-line "look ahead" controller might do the same with no LLM at all.

So we should add a simple non-LLM "look-ahead" baseline

Then if the LLM still wins, we can honestly say the language understanding helped, not just the timing. This keeps our comparison fair.

On "what format do we give the LLM?"

No one agrees

Whether JSON, a table or plain sentences works best depends on the model. No study tested it for control.

Numbers in sentences hurt

Tables or JSON tend to beat numbers buried in prose, and the format changes token count, so speed and cost too.

So we test it ourselves

Same controller, three formats (JSON / table / Low-Med-High words). A cheap experiment with a real result.

Questions for the team
